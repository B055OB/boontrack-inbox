## 2. POSTGRESQL ATOMICITY & ROW-LEVEL LOCKING EVIDENCE

### 2.1 Implementation in `packages/workforce-billing/ledger/postgres-tenant-pass-ledger.ts`
This implementation guarantees ACID transaction boundaries and PostgreSQL row-level locks across distributed containers:

```typescript
/**
 * packages/workforce-billing/ledger/postgres-tenant-pass-ledger.ts
 * PostgreSQL Production Adapter for BWM Tenant Pass Ledger (CTO Audit Compliance)
 *
 * Direct Database-Level Invariants:
 * 1. Transaction Boundaries: Explicit `BEGIN` ... `COMMIT` / `ROLLBACK`.
 * 2. Multi-Container Concurrency: Row-Level Locking via `SELECT ... FOR UPDATE` on tenant state.
 * 3. Anti-Negative Balance: DDL CHECK `balance_after >= 0` and application-level verification.
 * 4. Persistent Webhook Idempotency: `ON CONFLICT (idempotency_key) DO UPDATE SET retry_count = retry_count + 1`.
 */

import { Client, PoolClient } from 'pg';

export interface PostgresLedgerMutationParams {
  tenantId: string;
  batchId: string;
  deltaPasses: number;
  reason: 'PURCHASE' | 'ALLOCATION' | 'REVERSAL' | 'RENEWAL';
  idempotencyKey: string;
  metadata?: Record<string, any>;
}

export interface PostgresLedgerMutationResult {
  isDuplicate: boolean;
  entryId: string;
  tenantId: string;
  balanceAfter: number;
}

export interface PersistentWebhookIngestionParams {
  provider: string;
  eventId: string;
  idempotencyKey: string;
  eventType: string;
  rawPayload: any;
  headers: Record<string, string>;
}

export interface PersistentWebhookIngestionResult {
  inboxId: string;
  isDuplicate: boolean;
  retryCount: number;
  status: string;
}

export class PostgresTenantPassLedger {
  private readonly client: Client | PoolClient;
  private readonly targetSchema: string;

  constructor(client: Client | PoolClient, targetSchema: string = 'workforce_staging') {
    this.client = client;
    this.targetSchema = targetSchema;
  }

  /**
   * Executes atomic balance mutation inside PostgreSQL transaction with row-level locking.
   * Multi-instance/multi-container safe via `SELECT ... FOR UPDATE` and `CHECK (balance_after >= 0)`.
   */
  public async mutateBalanceAtomic(
    params: PostgresLedgerMutationParams
  ): Promise<PostgresLedgerMutationResult> {
    const { tenantId, batchId, deltaPasses, reason, idempotencyKey, metadata = {} } = params;

    await this.client.query('BEGIN');
    try {
      // 1. Enforce Idempotency Key Uniqueness at Database Level
      const existingRes = await this.client.query(
        `SELECT entry_id, balance_after FROM ${this.targetSchema}.tenant_pass_ledger WHERE idempotency_key = $1`,
        [idempotencyKey]
      );

      if (existingRes.rows.length > 0) {
        await this.client.query('COMMIT');
        return {
          isDuplicate: true,
          entryId: existingRes.rows[0].entry_id,
          tenantId,
          balanceAfter: existingRes.rows[0].balance_after,
        };
      }

      // 2. Multi-Container Concurrency Guard: Row-Level Locking via SELECT ... FOR UPDATE
      const lockRes = await this.client.query(
        `SELECT balance_after
         FROM ${this.targetSchema}.tenant_pass_ledger
         WHERE tenant_id = $1
         ORDER BY created_at DESC
         LIMIT 1
         FOR UPDATE`,
        [tenantId]
      );

      const currentBalance = lockRes.rows.length > 0 ? Number(lockRes.rows[0].balance_after) : 0;
      const newBalance = currentBalance + deltaPasses;

      // 3. Application pre-check for anti-negative balance (mirrored by PostgreSQL CHECK constraint)
      if (newBalance < 0) {
        throw new Error(
          `ERR_NEGATIVE_BALANCE: Requested delta ${deltaPasses} would reduce balance below zero (Current: ${currentBalance}, Result: ${newBalance})`
        );
      }

      // 4. Append Immutable Ledger Entry
      const entryId = `ple_${Date.now()}_${Math.random().toString(36).substring(2, 7)}`;
      await this.client.query(
        `INSERT INTO ${this.targetSchema}.tenant_pass_ledger (
          entry_id, tenant_id, batch_id, delta_passes, balance_after, reason, idempotency_key, metadata, created_at
        ) VALUES ($1, $2, $3, $4, $5, $6, $7, $8, NOW())`,
        [entryId, tenantId, batchId, deltaPasses, newBalance, reason, idempotencyKey, JSON.stringify(metadata)]
      );

      await this.client.query('COMMIT');

      return {
        isDuplicate: false,
        entryId,
        tenantId,
        balanceAfter: newBalance,
      };
    } catch (error) {
      await this.client.query('ROLLBACK');
      throw error;
    }
  }

  /**
   * Persistent Webhook Ingestion using PostgreSQL ON CONFLICT UPSERT semantics.
   */
  public async ingestPersistentWebhook(
    params: PersistentWebhookIngestionParams
  ): Promise<PersistentWebhookIngestionResult> {
    const { provider, eventId, idempotencyKey, eventType, rawPayload, headers } = params;

    const query = `
      INSERT INTO ${this.targetSchema}.workforce_webhook_inbox (
        provider, event_id, idempotency_key, event_type, raw_payload, headers, status, retry_count, received_at
      ) VALUES ($1, $2, $3, $4, $5, $6, 'RECEIVED', 0, NOW())
      ON CONFLICT (idempotency_key) DO UPDATE
        SET retry_count = ${this.targetSchema}.workforce_webhook_inbox.retry_count + 1
      RETURNING id, status, retry_count, (xmax = 0) AS is_new_delivery;
    `;

    const res = await this.client.query(query, [
      provider,
      eventId,
      idempotencyKey,
      eventType,
      JSON.stringify(rawPayload),
      JSON.stringify(headers),
    ]);

    const row = res.rows[0];
    const isNew = row.is_new_delivery;

    return {
      inboxId: row.id,
      isDuplicate: !isNew,
      retryCount: Number(row.retry_count),
      status: row.status,
    };
  }
}
```

### 2.3 Stored Procedure FIFO Locking (`packages/workforce-billing/schema/workforce-billing-schema.sql`)
Stored function executing row-level locks via `SELECT ... FOR UPDATE` with strict tenant boundary checks:

```sql
CREATE OR REPLACE FUNCTION fn_workforce_allocate_credit_fifo(
    p_tenant_id TEXT,
    p_branch_id TEXT,
    p_personnel_id TEXT,
    p_personnel_name TEXT
)
RETURNS TABLE (
    out_allocation_id TEXT,
    out_lot_id TEXT,
    out_personnel_id TEXT,
    out_activated_at TIMESTAMPTZ,
    out_expires_at TIMESTAMPTZ,
    out_remaining_lot_credits INT
)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = workforce_staging, extensions, public, pg_temp
AS $$
DECLARE
    v_lot RECORD;
    v_new_available INT;
    v_new_status VARCHAR(20);
    v_allocation_id TEXT;
    v_now TIMESTAMPTZ := NOW();
    v_expires_at TIMESTAMPTZ;
    v_conflicting_tenant TEXT;
BEGIN
    -- Guard 1: Tenant ID must be present
    IF p_tenant_id IS NULL OR TRIM(p_tenant_id) = '' THEN
        RAISE EXCEPTION 'ERR_CROSS_TENANT_VIOLATION: Empty or null tenant_id provided'
            USING ERRCODE = '28000';
    END IF;

    -- Guard 2: Cross-Tenant Breach Check
    -- If branch_id already has active/settled lots owned by a different tenant, reject fail-closed!
    SELECT id_lot.tenant_id INTO v_conflicting_tenant
    FROM workforce_credit_lots id_lot
    WHERE id_lot.branch_id = p_branch_id
      AND id_lot.tenant_id <> p_tenant_id
    LIMIT 1;

    IF v_conflicting_tenant IS NOT NULL THEN
        RAISE EXCEPTION 'ERR_CROSS_TENANT_VIOLATION: Branch % is registered to tenant %, unauthorized access by %',
            p_branch_id, v_conflicting_tenant, p_tenant_id
            USING ERRCODE = '28000';
    END IF;

    -- Step 1: Lock oldest active lot belonging STRICTLY to p_tenant_id and p_branch_id (FIFO)
    SELECT id_lot.lot_id, id_lot.available_credits, id_lot.consumed_credits, id_lot.status
    INTO v_lot
    FROM workforce_credit_lots id_lot
    WHERE id_lot.tenant_id = p_tenant_id
      AND id_lot.branch_id = p_branch_id
      AND id_lot.status = 'ACTIVE'
      AND id_lot.available_credits > 0
    ORDER BY id_lot.created_at ASC
    LIMIT 1
    FOR UPDATE;

    -- Invariant: If no lot has available credits under p_tenant_id, fail-closed immediately
    IF v_lot.lot_id IS NULL THEN
        RAISE EXCEPTION 'ERR_INSUFFICIENT_CREDITS: Branch % available balance is 0 for tenant %',
            p_branch_id, p_tenant_id
            USING ERRCODE = '55000';
    END IF;

    -- Step 2: Atomic decrement
    v_new_available := v_lot.available_credits - 1;
    IF v_new_available = 0 THEN
        v_new_status := 'DEPLETED';
    ELSE
        v_new_status := 'ACTIVE';
    END IF;

    UPDATE workforce_credit_lots
    SET available_credits = v_new_available,
        consumed_credits = v_lot.consumed_credits + 1,
        status = v_new_status,
        updated_at = v_now
    WHERE workforce_credit_lots.lot_id = v_lot.lot_id
      AND workforce_credit_lots.tenant_id = p_tenant_id;

    -- Step 3: Compute 30-day active window
    v_expires_at := v_now + INTERVAL '30 days';
    v_allocation_id := 'ALC-' || TO_CHAR(v_now, 'YYYYMMDDHH24MISSMS') || '-' || SUBSTRING(MD5(RANDOM()::TEXT), 1, 6);

    -- Step 4: Record allocation with tenant_id scoping
    INSERT INTO workforce_credit_allocations (
        allocation_id,
        lot_id,
        tenant_id,
        branch_id,
        personnel_id,
        personnel_name,
        activated_at,
        expires_at,
        status
    ) VALUES (
        v_allocation_id,
        v_lot.lot_id,
        p_tenant_id,
        p_branch_id,
        p_personnel_id,
        p_personnel_name,
        v_now,
        v_expires_at,
        'ACTIVE'
    );

    -- Return output tuple
    out_allocation_id := v_allocation_id;
    out_lot_id := v_lot.lot_id;
    out_personnel_id := p_personnel_id;
    out_activated_at := v_now;
    out_expires_at := v_expires_at;
    out_remaining_lot_credits := v_new_available;
    RETURN NEXT;
END;
$$;
```

### 2.4 Multi-Container / Multi-Instance Race Condition Protection Architecture
In high-concurrency production deployments (e.g., Kubernetes pods, ECS tasks, or Railway replicas):
1. **Zero Reliance on In-Memory Mutexes:** While Node.js in-memory mutexes (`acquireTenantLock`) protect against concurrency within a single Node.js process, cross-instance safety is 100% delegated to PostgreSQL kernel-level Row-Level Locks (`SELECT ... FOR UPDATE`).
2. **PostgreSQL Row-Level Locking:** When Pod A and Pod B concurrently execute `fn_workforce_allocate_credit_fifo` or `mutateBalanceAtomic` for the same `tenant_id`, the second container's query blocks at the database kernel level until the first container issues `COMMIT` or `ROLLBACK`.
3. **Database-Level Fail-Closed Invariants:**
   - `CONSTRAINT chk_tenant_ledger_balance_non_negative CHECK (balance_after >= 0)`
   - `available_credits INT NOT NULL CHECK (available_credits >= 0)`
   If any concurrent transaction attempts to overdraw the balance, PostgreSQL rejects the transaction with code `23514 (check_violation)`, triggering an automatic transactional `ROLLBACK`.

#### Replay Detection Mechanism via PostgreSQL `xmax`:
- When an event arrives for the **first time**, PostgreSQL inserts a new row. The internal system column `xmax` is `0`, returning `is_new_delivery = true`. The payment is credited.
- When an event is **replayed** (2nd to 10th time), PostgreSQL detects the conflict on `idempotency_key UNIQUE` and executes `DO UPDATE SET retry_count = retry_count + 1`. Because an existing row was modified, `xmax <> 0`, returning `is_new_delivery = false`.
- Application logic checks `is_new_delivery`: if `false`, it immediately returns HTTP 200 OK without mutating the credit ledger or altering balances.
